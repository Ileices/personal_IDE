## Plan: AI Coding Assistant Web App with Memory System

Build a local web-based AI coding IDE that connects to your GitHub Copilot models via the **GitHub Models API** (`models.github.ai`), with a chat UI, ask/edit/plan/agent modes, a persistent project memory system (SQLite), and an autonomous agent loop that parses structured LLM output to continuously execute coding tasks — all with a consumer-friendly UI.

### Steps

1. **Scaffold a TypeScript monorepo** — Create a `pnpm` workspace at personal_IDE/ with three packages: `apps/web` (React + Vite frontend), `apps/server` (Node.js + Fastify backend), and `packages/shared` (common types & constants). This keeps every feature modular in small, focused files.

2. **Build the LLM client & model selector** — In `apps/server/src/services/llm/`, create an OpenAI-SDK-based client pointed at `https://models.github.ai/inference` using your GitHub PAT. Expose a `/api/models` route listing available models (GPT-4.1, o3, DeepSeek-R1, Grok-3, etc.) and a `/api/chat` SSE-streaming route. The frontend gets a dropdown model picker wired to this.

3. **Implement the four modes (Ask / Edit / Plan / Agent)** — Each mode is a separate backend service module (`ask.ts`, `edit.ts`, `planner.ts`, `loop.ts`) with a shared interface. A tab bar in the frontend switches modes. *Ask* = simple chat. *Edit* = file-targeted diffs with approve/reject. *Plan* = step list review. *Agent* = autonomous loop (step 5).

4. **Build the filesystem bridge** — A backend module (`apps/server/src/services/filesystem/`) exposes REST routes for listing, reading, writing, and searching files in a user-selected project folder. The frontend renders a file tree and embeds **Monaco Editor** (the same editor VS Code uses) for viewing/editing code. All writes are sandboxed to the project root with path-traversal guards and automatic `.bak` snapshots before changes.

5. **Create the project memory system (SQLite)** — A local SQLite database stores: `projects`, `conversations`, `memory_notes` (tagged, searchable context), `file_summaries`, and `agent_runs`. A `/api/memory` CRUD API lets the frontend show a "New Project / Load Project" control panel. Every LLM response is parsed for an **end-of-task summary** (forced via system prompt) and auto-inserted into `memory_notes`. On each new prompt, the server runs a keyword/semantic search against memory to inject relevant past context into the system message.

6. **Build the autonomous agent loop with structured output** — The agent mode uses a **state machine** (IDLE → PLANNING → EXECUTING → EVALUATING → COMPLETE). The LLM is forced (via system prompt + JSON-mode) to return a strict schema: `{ "summary": "...", "files_changed": [...], "next_steps": [{ "action": "...", "target": "...", "detail": "..." }], "questions_for_user": [...], "done": false }`. A parser in `apps/server/src/services/agent/parser.ts` extracts `next_steps` and re-formats them as imperative commands (never questions), then feeds them back as the next user message. `questions_for_user` are written to a capped log folder (`memory/questions/`) and auto-answered by having the LLM review the codebase. Timing controls (interval delays, max iterations, token budgets) and a **Stop** button are exposed in the UI.

### Further Considerations

1. **Rate limits are tight on the free tier** (50–150 requests/day for most models, 8 req/day for GPT-5/o3) — the agent loop will burn through these fast. Recommend enabling **GitHub Models paid usage** ($0.00001/token-unit) for agent mode, or building an auto-fallback that switches to cheaper models (GPT-4.1-mini → Llama) when limits approach. Should I plan a rate-limit dashboard into the UI?

2. **Security model for filesystem access** — The backend will have full read/write to your disk. Should we add a confirmation modal for all file writes (safer, slower) or allow agent mode to write freely within the project folder (faster, riskier)? I recommend a toggle: "require approval" for Edit mode, "auto-approve within project" for Agent mode with undo history.

3. **Deployment** — This is designed to run locally (`localhost:3000`). If you ever want to access it from other devices (phone/tablet), we'd add a simple auth layer. For now, local-only keeps it simple. Does that work?

## Plan: Prototype-Driven Knowledge Graph & Dev-Mode Instructions

Your prototype is genuinely impressive — it's a 6,300-line industrial-grade Python integration engine that does things our IDE currently **cannot do at all**: AST-based symbol resolution, dependency graph construction, namespace conflict detection, module clustering, safety scoring, and sandbox testing. The IDE currently relies entirely on regex and LLM calls for code understanding — it has **zero semantic analysis**.

The core insight from your prototype is this: **the LLM can't safely edit line-by-line in a massive codebase unless it has a searchable, indexed map of every symbol, every import relationship, every cross-file dependency, and every conflict risk.** Your prototype builds exactly that map — but only for Python, and only at build-time. We need a persistent, multi-language, continuously-updated version of it baked into the IDE's memory architecture.

Here's what should happen:

### Steps

1. **Create a multi-language Code Relationship Index service** — new file apps/server/src/services/analysis/relationshipIndex.ts. This is the IDE equivalent of your prototype's `analyze_imports`, `build_dependency_map`, `detect_namespace_conflicts`, and `analyze_function_compatibility`. Uses **tree-sitter** (via `tree-sitter` npm + grammars for TS, JS, Python, Rust, Go, C, C++, C#, Java, HTML, CSS) for real AST parsing across all languages. Builds a persistent SQLite-backed graph of: symbols (functions, classes, variables, types), imports/exports, cross-file references, call chains, and conflict risks. Exposes hotword-tagged searchable entries (e.g. `"UserService.getById → imports → DatabasePool from ../../db/pool.ts"`) that get injected into LLM context on demand.

2. **Create a Code Knowledge Graph DB layer** — new tables in index.ts: `code_symbols` (id, project_id, file_path, name, kind, signature, line_start, line_end, scope, purity_score, domain), `code_relationships` (source_symbol_id, target_symbol_id, relationship_type [imports, calls, extends, implements, re-exports]), `code_conflicts` (id, project_id, symbol_a_id, symbol_b_id, conflict_type, resolution_strategy, resolved), `code_edit_log` (id, project_id, file_path, line_start, line_end, old_content_hash, new_content_hash, agent_run_id, timestamp). This is the "hotword memory" — every symbol becomes a searchable log entry with full relationship context.

3. **Create a Log Bloat Manager** — new file apps/server/src/services/analysis/logManager.ts. Ported concept from your prototype's `AdvancedLogger` with buffered writes, error correlation, and rotation — but adapted for the knowledge graph. Implements tiered retention: hot (current session symbols, <1hr), warm (recently-accessed relationships, <24hr at full detail), cold (compressed summaries, archived). Auto-compacts the `code_symbols` and `code_relationships` tables when row counts exceed configurable thresholds (e.g. 500K symbols → merge, deduplicate, summarize low-importance entries). Shares compacted context with the LLM via the chunking pipeline so no blind editing occurs.

4. **Create a Project Tier & Language Decision Engine** — new file apps/server/src/services/modes/projectTierEngine.ts. Hardcoded decision matrix: user selects tier (Prototype → Production → Enterprise → Global-Scale), engine resolves to language stack, architecture pattern, and complexity rules. E.g., Prototype="single language, monolith, minimal deps", Enterprise="3-8 languages, microservices, CI/CD, monitoring", Global="10-100+ languages/data formats, distributed, multi-region". When user says "build me a Diablo-like game", the engine resolves tier → languages (C++ engine + Lua scripting + GLSL shaders + JSON data + Python tools), then injects the full stack decision into the agent's system prompt as a non-negotiable architectural constraint.

5. **Rewrite `buildAgentSystemPrompt` with full-dev-mode instructions** — modify agentPrompts.ts. Inject three new mandatory instruction blocks: (A) **Relationship-Aware Editing** — before modifying ANY line, the LLM must query the knowledge graph for all symbols on that line, all files that import/call those symbols, and all potential conflicts; include the query results in its reasoning. (B) **Mandatory Edit Logging** — every line change must emit a structured log entry with old/new content hash, affected symbols, and downstream impact list. (C) **Corpus-Scale Instructions** — for projects exceeding 100K lines, the LLM must work in "surgical mode": never regenerate a full file, only emit line-range patches with full relationship context. For 9M+ line projects, the chunking pipeline processes the knowledge graph index (not raw code) to fit in context.

6. **Wire the pre-computation pipeline into the agent loop** — modify enhancedLoop.ts. Before Phase 0 (environment analysis), add Phase -1: "Relationship Index Build". Runs the tree-sitter parser across all project files, populates `code_symbols` and `code_relationships` tables, detects conflicts, and scores every file's integration risk (ported from your prototype's `assess_code_safety`). This happens ONCE per project load and incrementally on file changes. The index is then available to the LLM via hotword queries — when the LLM mentions a symbol name, the system auto-injects that symbol's full relationship chain into the next prompt. This is the automation that saves tokens: instead of sending raw code, send the pre-computed relationship graph.

### Further Considerations

1. **Tree-sitter vs. LLM-based analysis**: Tree-sitter gives real ASTs for 40+ languages (free, fast, offline) but requires installing grammar packages (~2MB each). For languages without tree-sitter support, fall back to regex extraction (current approach) plus an LLM summarization pass. Recommend tree-sitter as primary, LLM as fallback — this mirrors your prototype's AST-first approach but scales to all languages. **Do you want tree-sitter installed as a dependency, or prefer a pure LLM/regex approach to keep the dependency footprint small?**

2. **9M-line corpus handling**: At 9M lines, the knowledge graph itself could be 500K+ symbol entries. The log bloat manager's tiered retention handles this, but initial indexing could take 10-30 minutes. Should this run as a background process with progress reporting to the frontend, or block until complete? The chunking pipeline would process the *index* (not raw code) to fit any model context — even an 8K context model could work on a 9M-line project by querying the graph for only the relevant subgraph per task.

3. **Your prototype's functions that should become direct automations (not LLM instructions)**: `detect_system_commands` → security gate before executing any agent-generated shell commands. `assess_code_safety` → risk score injected into every file change event. `test_module_isolated` → sandbox testing before committing agent changes. These save tokens by doing the work pre-LLM rather than asking the LLM to reason about safety. **Want these as hard automation gates (block unsafe changes automatically) or advisory (show warnings but let the LLM proceed)?**
