## 1. Core Objective

**What you are building:** A fully autonomous, self-improving local-first IDE where an LLM agent doesn't just answer questions — it *reads, understands, writes, tests, and debugs entire codebases* across unlimited iterations, while simultaneously training a swarm of 296 purpose-built micro neural networks (the "Nano Sea") that will eventually replace the cloud LLMs entirely.

**Intended user:** A solo developer (or small team) who wants an AI pair-programmer that operates as a *persistent, stateful co-worker* — not a stateless chatbot. The user gives a high-level task ("build me a game," "refactor this module"), walks away, and comes back to working code with checkpoints for rollback safety.

**Core problem solved:** Current AI coding tools are *amnesiac and disconnected*. They lose context between messages, don't understand the codebase they're editing, produce contradictory architectures, and can't recover from errors autonomously. This project attacks all four problems: persistent memory, hierarchical code indexing, forced codebase exploration before writing, and multi-iteration error recovery with model-switching.

**Key features (by criticality):**
1. **Autonomous agent loop** — multi-iteration code generation with structured output, error auto-fix, test auto-run, and checkpoint rollback
2. **12-provider LLM abstraction** — seamless failover across GitHub Models, Ollama, Groq, Gemini, OpenRouter, LM Studio, Nano Sea, etc.
3. **Nano Sea** — 296 micro neural networks with P2P mesh networking, RESPECT-scored compute sharing, and self-evolving lifecycle management
4. **Fleet mode** — parallel multi-agent execution with role specialization (lead, implementer, debugger, tester, reviewer)
5. **Hierarchical codebase indexing** — AST-level code understanding with token-budget-aware rendering and forced read-before-write gating

## 2. Implementation Audit

### 2.1 What's Built — Inventory

| Layer | Components | State |
|-------|-----------|-------|
| **Frontend** | 36 React components, 9 Zustand stores, Monaco editor, SSE streaming | Functional |
| **API** | 20 Fastify route modules, WebSocket events, Zod validation | Functional |
| **Agent Engine** | enhancedLoop.ts (1,004 LOC) + 14 `loop/` modules (3,191 LOC) + 4 `indexer/` modules (1,828 LOC) | Functional, recently wired |
| **LLM Layer** | 12 providers, rate limiter, chunking pipeline, model switching | Functional |
| **Analysis** | depGraph, moduleClustering, codebase analyzer, relationship index, log manager, tier engine | Mostly wired |
| **Memory** | SQLite-backed notes, file summaries, conversation indexing, knowledge graph | Functional |
| **Fleet** | Multi-agent orchestrator with role decomposition and file locking | Functional |
| **Nano Sea** | 296 nanos, orchestrator, mesh networking, RESPECT scoring, P2P | Functional (Python) |
| **Infrastructure** | CI/CD (4 jobs), crypto (AES-256-GCM), checkpoints (git-based), CSRF protection | Functional |
| **Database** | 17 tables across 2 migrations, WAL mode, parameterized queries | Functional |

**Architecture pattern:** Event-driven monolith with module extraction trending toward plugin architecture. The server is a single Fastify process. The Nano Sea is a separate Python/FastAPI process managed as a subprocess. Communication is HTTP + WebSocket. There is no message queue.

**Data flow** (abbreviated):
```
Browser → Zustand store → fetch/SSE → Fastify route → EnhancedAgentLoop
  → assembleContext (memory + codebase + hierarchy + depGraph + errors)
  → LLM call (with rate limit/failover/chunking)
  → processResponse (parse output → write files → lint → test → checkpoint)
  → SSE events back to browser
```

### 2.2 Over-Engineered Elements

**A. The Nano Sea is a research project disguised as a feature dependency (296 nanos × 19 categories).** The entire `NANO_train/` subsystem — 171 Python files, mesh networking, RESPECT scoring, Hebbian ripple propagation, PTAIE scheduling, IC-AE recursive infection, Absularity lifecycle detection — represents an *extraordinary* amount of conceptual ambition. However:
- The nanos are 3-layer MLPs with <50K parameters each. A single `codellama:7b` has 7 *billion* parameters. The 296 nanos combined have ~15M parameters — roughly 0.2% of the smallest useful code model.
- The mesh P2P system (2,329 lines) solves a distributed compute problem that doesn't exist yet — you'd need the nanos to actually produce useful completions first.
- The RESPECT scoring, PTAIE vectors, RBY color theory, and Absularity detection are *novel theoretical frameworks* that add conceptual overhead without empirical validation. Every developer who touches this code must first understand an entirely custom ontology.
- **Impact:** ~6,000 lines of Python maintaining infrastructure for a system that currently returns fallback messages (per the User Manual: "Initially returns fallback messages until nanos are trained").

**B. The analysis subsystem has too many small, overlapping modules.** Under analysis/, there are 15+ files (codebase.ts, depGraph.ts, moduleClustering.ts, codeAnalysis.ts, codeSanitizer.ts, conversationIndexer.ts, errorPatterns.ts, importExtractors.ts, logManager.ts, moduleClassifier.ts, projectTierEngine.ts, relationshipIndex.ts, safetyScorer.ts, symbolPatterns.ts) that each handle a narrow slice of code understanding. Several are partially redundant:
  - `importExtractors.ts` parses imports; so does astParser.ts (818 lines)
  - `relationshipIndex.ts` builds symbol graphs; so does `depGraph.ts` — at different granularities but with overlapping data
  - `codebase.ts` (521 lines) does its own file scanning; so does fsWalker.ts (323 lines) and codeIndexer.ts (518 lines)

**C. The 4-tier project tier engine** (`projectTierEngine.ts`) auto-classifies projects as prototype/production/enterprise/global and adjusts behavior accordingly. This is premature — the IDE is a single-user local tool. The tier engine adds branching complexity to prompts and context assembly for a scaling scenario that doesn't exist.

**D. Fleet mode role decomposition is over-specified.** fleet.ts (703 lines) implements 6 agent roles with file-lock conflict avoidance. In practice, all agents hit the same rate limits on the same provider, so fleet mode is bottlenecked by API quota, not by orchestration sophistication.

### 2.3 Under-Developed Elements

**A. Testing is critically thin.** 4 E2E test files exist in testing/ but they test only basic lifecycle (start/stop/pause) and Zod validation. There are:
- **Zero unit tests** for the 14 `loop/` modules (3,191 lines of core logic untested)
- **Zero unit tests** for the hierarchical indexer (1,828 lines)
- **Zero unit tests** for the chunking pipeline (534 lines)
- **Zero unit tests** for the rate limiter (476 lines)
- **Zero integration tests** for the agent-to-LLM round-trip
- The CI/CD pipeline checks types and runs the 4 E2E files, but the E2E tests themselves note they "require running server" and are only done in staging

**B. Authentication is dangerously minimal.**
- No session tokens — auth state is a single row in `auth_tokens` marking the "active" account
- No middleware-based auth — each route must manually check auth inline
- The CSRF plugin validates Origin/Referer headers, but there's no JWT, no cookie signing, no request-level auth verification
- Guest mode has unrestricted access to all endpoints, including file write and agent start
- API keys are encrypted at rest (AES-256-GCM), but the encryption key is auto-generated and stored as a plaintext `.env` entry

**C. The astParser.ts (818 lines) uses regex, not a real parser.** Every language-specific function (`parseTSFileNode`, `parsePyFileNode`, `parseRustFileNode`, `parseGoFileNode`) relies on line-by-line regex matching. This will:
- Miss multi-line signatures, decorators spanning lines, nested classes
- Misidentify string literals containing keywords (`const x = "class Foo"`)
- Fail on any non-trivial metaprogramming (decorators, macros, generics with constraints)
- The decision to avoid tree-sitter is understandable for zero-dependency simplicity, but it's the single biggest accuracy risk in the indexing pipeline

**D. No file-watching or incremental rebuild.** The hierarchical index (hierarchicalIndex.ts) rebuilds on each agent run via `buildIndex()`. There's an `incrementalUpdate()` method, but it's triggered manually — there's no `fs.watch` or chokidar integration. If files change between agent runs (user edits in another editor), the index is stale.

**E. The WebSocket layer is fire-and-forget.** The server broadcasts SSE/WebSocket events to all connected clients with no per-client filtering, no reconnection handling, and no event replay on reconnect. If the browser tab disconnects and reconnects mid-agent-run, all intermediate events are lost.

**F. No database backup or migration rollback.** The migration system (db/index.ts, 340 lines) runs forward-only. There's no `down` migration. If migration v2 corrupts data, the only recovery is deleting `ide.db` and losing all memory, conversations, and provider configs.

**G. The Midwife training pipeline has no validation loop.** midwife/index.ts (520 lines) generates synthetic training data by having cloud LLMs produce code-completion pairs, then feeds them to the Nano Sea. But there's no evaluation step — no holdout set, no accuracy measurement, no rejection of bad training data. The nanos train on whatever the LLM produces, including hallucinated or incorrect code.

## 3. Capability & Gap Analysis

### What the project **cannot** currently achieve:

| Limitation | Severity | Explanation |
|-----------|----------|-------------|
| **Nano Sea cannot replace cloud LLMs** | Critical | 296 nanos × <50K params = ~15M total parameters. GPT-4.1-mini alone has billions. The nanos can't generate coherent multi-line code. The "self-improving" aspiration requires orders of magnitude more training data, compute, and architectural innovation (MoE, attention mechanisms, etc.). |
| **No multi-user support** | High | Single SQLite database, single active auth token, no user isolation. Cannot serve two users simultaneously without data leakage. |
| **Cannot survive server restart mid-agent-run** | High | Agent loop state (iteration count, conversation history, pending tasks) lives entirely in memory. A server crash loses the run. The checkpoint system preserves *file changes* but not *loop state*. |
| **Cannot handle large codebases (>10K files)** | Medium | fsWalker.ts walks the entire filesystem synchronously on each index build. astParser.ts reads every file into memory. A monorepo with 50K files would cause multi-minute blocking pauses and OOM risk. |
| **Cannot produce reliable code for unfamiliar stacks** | Medium | The exploration gate forces reading before writing, but the agent has no external documentation retrieval beyond basic web search. If the target framework isn't in the LLM's training data, the agent will still hallucinate APIs. |
| **Cannot run in production (multi-tenant, internet-facing)** | High | No rate limiting per user (beyond basic IP throttle), no input sanitization on agent task descriptions, no sandboxing of `toolExecutor.ts` shell commands, no resource limits on agent runs. A malicious task description could execute arbitrary commands. |
| **Fleet mode is bottlenecked by API quota** | Medium | All fleet agents share the same provider credentials. 4 agents on GitHub Models free tier will exhaust rate limits in seconds. Fleet is only practical with local providers (Ollama) or paid API tiers. |
| **No offline-first capability** | Low | Despite being "local-first," the IDE requires at least one LLM provider to be accessible. If Ollama isn't installed and all cloud providers are rate-limited, the system is inert. |

## 4. Technology & Language Recommendations

### 4.1 Current Stack Assessment

| Component | Current | Verdict |
|-----------|---------|---------|
| **TypeScript + Fastify** | Server | ✅ **Keep.** Type safety is essential at this complexity level. Fastify's plugin architecture fits. |
| **React 19 + Zustand + Vite** | Frontend | ✅ **Keep.** Modern, fast, minimal boilerplate. Zustand's simplicity is appropriate for 9 stores. |
| **SQLite (better-sqlite3)** | Database | ⚠️ **Keep for now, but it's the ceiling.** WAL mode handles single-user well. Multi-user or concurrent agent fleet writes will hit SQLite's single-writer lock. |
| **Python + PyTorch** | Nano Sea | ⚠️ **Keep PyTorch, but challenge the nano architecture.** 3-layer MLPs can't do code completion. |
| **pnpm monorepo** | Package management | ✅ **Keep.** Clean workspace separation. |
| **Tailwind CSS** | Styling | ✅ **Keep.** Appropriate for rapid UI iteration. |

### 4.2 Recommended Additions

**A. Add tree-sitter for AST parsing** — *Priority: HIGH*

The 818-line regex parser in astParser.ts is the weakest link in the indexing pipeline. `tree-sitter` (via [`tree-sitter`](https://www.npmjs.com/package/tree-sitter) or [`web-tree-sitter`](https://www.npmjs.com/package/web-tree-sitter)) provides:
- Correct parsing of 30+ languages with zero regex maintenance
- Incremental re-parsing (only re-parse changed regions)
- Query support (S-expression patterns to extract symbols)
- Battle-tested in VS Code, Neovim, GitHub Linguist

**Justification:** Every downstream consumer (hierarchical index, depGraph, exploration gate) depends on accurate symbol extraction. Regex-based parsing will accumulate silent errors that compound into incorrect codebase understanding — the exact failure mode the exploration gate was built to prevent.

**B. Add Vitest unit tests for core modules** — *Priority: HIGH*

The 14 `loop/` modules and 4 `indexer/` modules total 5,019 lines of critical business logic with zero unit tests. Recommended coverage targets:

| Module | Why |
|--------|-----|
| `rateLimiter.ts` | Incorrect rate limiting causes agent halts or API bans |
| `tokenRecovery.ts` | Token budget miscalculation causes 413 errors or wasted context |
| explorationGate.ts | Gate logic errors either block all work or skip exploration entirely |
| `hierarchicalIndex.ts` | Index corruption silently degrades every agent run |
| responseProcessing.ts | File write logic is the most destructive code path |
| `contextAssembly.ts` | Budget allocation errors either starve or overflow the context window |

**Justification:** You're building a system that *autonomously writes and modifies code*. Untested code writing untested code is a compounding reliability risk.

**C. Add `chokidar` for filesystem watching** — *Priority: MEDIUM*

Replace manual `buildIndex()` calls with an `fs.watch`-based incremental updater. When the user edits files outside the agent (in VS Code, vim, etc.), the hierarchical index should auto-update within seconds.

**Justification:** The hierarchical index is only useful if it reflects the current filesystem state. Without watching, the index goes stale between agent runs, and the exploration gate operates on outdated information.

**D. Add structured agent state persistence** — *Priority: MEDIUM*

Currently, if the server crashes mid-agent-run, the run is lost. Add a `agent_run_state` table that checkpoints the full loop state (current iteration, accumulated context, pending task, model config) every N iterations. On server restart, offer to resume interrupted runs.

**Justification:** Autonomous agent runs can take 30+ minutes with 50 iterations. Losing an entire run to a Node.js OOM or power outage is a terrible user experience.

**E. Replace the Nano Sea's 3-layer MLPs with a Mixture-of-Experts transformer** — *Priority: LOW (research)*

The 296-nano swarm is architecturally novel but computationally insufficient for code generation. Consider:
- A single small transformer (e.g., 125M params) with 296 expert heads (one per nano category)
- Each "nano" becomes a routing decision, not a separate model
- Training uses the same Midwife pipeline but with proper evaluation (holdout accuracy, BLEU, pass@k)
- This preserves the swarm metaphor while producing actually-useful completions

**Justification:** The current architecture will never produce coherent code completions. The 296 nanos are interesting as a *research contribution* but cannot serve as an LLM replacement without fundamental architectural changes.

**F. Add Docker Compose for reproducible deployment** — *Priority: LOW*

A `docker-compose.yml` with three services (server, web, nano-sea) would:
- Eliminate "works on my machine" issues
- Enable one-command setup (`docker compose up`)
- Isolate the Nano Sea's Python dependencies from the host
- Make CI/CD testing more realistic

**Justification:** The current setup requires Node.js 20+, pnpm 9+, Python 3.11+, PyTorch, and optionally CUDA — a fragile dependency chain that the setup scripts partially address but don't fully guarantee.

### 4.3 What NOT to Add

| Technology | Why Not |
|-----------|---------|
| **PostgreSQL / MySQL** | SQLite is sufficient for single-user. Adding a database server increases deployment complexity for zero benefit at current scale. |
| **Redis / message queue** | The agent loop is inherently sequential (one LLM call at a time). Fleet mode parallelism is per-agent, not per-message. A message queue adds latency without solving a real bottleneck. |
| **Next.js / SSR** | This is a local IDE, not a public website. CSR with Vite is appropriate. |
| **GraphQL** | The API surface (20 route modules) is well-mapped to REST. GraphQL's complexity tax isn't justified for a single-consumer API. |
| **Kubernetes** | This is a personal IDE. K8s would be absurd over-engineering. |
