## SECTION A — THE LLM INFRASTRUCTURE LAYER (Passes 1-3 missed this entirely)

### Finding 1 — Smart Chunking Pipeline With LLM-Generated Bridge Summaries EXISTS

**Pass 1 asked:** "crawlers need smart chunking and algorithmic overlapping coverage." This system IS built.

`services/llm/chunkingPipeline.ts` is a complete automatic chunking pipeline:
- Splits oversized content into model-sized chunks using a three-fraction budget: 75% for data, 12.5% for bridge context, 12.5% for system prompt overhead
- Between every chunk pair, it calls the LLM to generate a `bridgeSummary` — a running compressed summary of everything processed so far
- Next chunk gets: "PREVIOUS RUNNING SUMMARY: [compressed] + LATEST CHUNK ANALYSIS: [current]" — no raw overlap, actual LLM-summarized continuity
- Recursive sub-pipeline splitting with configurable `maxRecursionDepth` prevents stack overflow on deeply nested content
- Has progress events: `chunk_start`, `chunk_complete`, `bridge_generated`, `pipeline_complete`, `pipeline_error`
- `ChunkingPipelineConfig` exposes: chunkFraction (0.75), bridgeFraction (0.125), overheadFraction (0.125), maxOutputTokens (4096), temperature (0.3)

bridgeSummarizer.ts prompt instructs the LLM: "Include: key findings, important file paths, function names, patterns discovered, decisions made. Drop: verbose explanations, code blocks, duplicate information. This summary will be used as context for processing the remaining N parts."

**Gap that remains:** This pipeline handles data that's too large for a single context window. It's NOT the same as the semantic embedding/clustering approach needed for true codebase understanding. It's sequential chunk processing, not simultaneous multi-perspective analysis. Still missing: overlapping windows across file boundaries, semantic clustering of related code before chunking.

### Finding 2 — Production Rate Limiter With Real GitHub Header Tracking

`services/llm/rateLimiter.ts` — ported from github_api_limit_prototype:
- **Primary limits**: reads `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-reset` from actual API response headers. Falls back to local counting if headers absent.
- **Secondary limits** (abuse detection): exponential backoff doubling on each 429/403, resets on success. Points window (mutative write = 5pts, read = 1pt). Retry-after header respected.
- `maxGlobalConcurrent = 5` global concurrent requests cap
- Safety margin: stops when remaining falls to 10% of server-reported limit
- **Dead model blacklist**: models that return 404 are blacklisted with a TTL to prevent infinite fallback loops
- `findFallback(model, caller, chain?)` — finds next working model in the fallback chain, skipping dead/rate-limited models
- `acquire()` returns: `{ allowed, reason, retryAfterMs, fallbackModel }` — caller gets suggested alternative when blocked

**Gap:** The rate limiter is per-provider/model but not per-user. The `userRateLimiter.ts` exists separately — they're two separate systems that must both be satisfied.

### Finding 4 — The Actual LLM System Prompt Architecture

`services/modes/agentPrompts.ts` — "NASA-Grade Automation System Prompts v2" reveals exactly what God Factory tells the LLM:

**Three-part prompt structure (designed to survive truncation):**

2. Main body — FILE_CHANGE_FORMAT (`--- FILE: path ---` markers), STRUCTURED_OUTPUT_BLOCK (required JSON schema with summary, filesChanged, nextSteps, questionsForUser, done, confidence, commands, editLog)
3. `SCHEMA_REMINDER_FOOTER` — placed at BOTTOM. Repeats the JSON output requirement.

**What the structured output schema enforces:**
- `nextSteps`: always imperative ("Create X", "Add Y to Z"), never questions

### Finding 12 — ContextWindowManager Is a Priority-Based Slot Packer With Forensic Logging

`services/contextWindowManager/index.ts` — not just truncation, it's a full priority packing system:
