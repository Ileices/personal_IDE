### Finding 11 — Agent Meta-Architecture From lump Folder Directly Describes What God Factory Should Become

**The agent_meta_architecture_action_plan.json (5-phase build plan) describes:**
- Phase 1: Memory fabric — token-aware index manager with 60% keyword overlap + 25% recency + 15% frequency scoring. Overflow queue for memories that don't fit context budget.
- Phase 2: Memory writer — persists every user turn and agent turn to disk with UUID filenames. Registered in a master index.
- Phase 3: Script executor — agent writes Python automation SCRIPTS that write the code. Agent only sees compressed summaries. "The agent is a control plane, not a code writer."

- Phase 5: Self-improvement — after each run, scores its own output, updates access counts, prunes low-value memories

**The key design principle stated verbatim:** "A 512-token model build arbitrarily large codebases across many turns" by generating scripts that generate code, never seeing the full output.

**Comparison to current God Factory:** The current God Factory agent does have some memory infrastructure (MemoryService with 10K notes per project, Pass 1). BUT it doesn't score memories by keyword overlap/recency/frequency, doesn't have an overflow queue, doesn't write automation scripts (it writes code directly), and doesn't compress its output. The meta-architecture from the lump folder is the blueprint for the next version of God Factory.

## SECTION C — CROSS-SYSTEM GAPS IDENTIFIED (Pass 3 Only)

### Gap: Three Codebase Analyzers With Zero Cross-Talk

PSC (regex devtags), HierarchicalCodeIndex (AST token budget), and RelationshipIndexService (symbol graph + imports) all analyze the same codebase. None share data. RelationshipIndexService has `formatForLLM()` that produces structured context text — this could replace or augment what God Factory currently gets from the idleScanner. But the knowledge graph is never injected into the agent context.

### Gap: Corpus Manifesto Not Connected to Agent Loop

The corpus manifesto system (routes/corpus.ts) generates a 512-token compressed summary of the entire project. This is exactly what God Factory needs at session start. Currently God Factory builds its context from memory notes + idle scanner + PSC drift events. The corpus manifesto is built and stored but never read by the agent orchestration layer.

### Gap: DatasetBuilder → NANO Training Handoff Not Automated

DatasetBuilder writes JSONL to agent_dataset. The Midwife service (Pass 2) has 9 task types but reads from its own internal queue, not from this file path. The bridge is one-directional and not closed-loop: files accumulate but no watcher kicks off Midwife ingestion when new training pairs arrive.

### Gap: ProjectTierEngine Detects But Doesn't Enforce

The tier engine detects a project's tier and returns required quality gates. But when God Factory or the agent loop makes changes to a project, it doesn't call `GET /api/tiers/:projectId` to determine what quality gates to apply before committing. A prototype-tier project could get enterprise-scale validation; a global-tier project could skip compliance checks.

### Gap: Feature Flags Are In-Memory Only

`runtimeFlags` in features.ts is a module-level `const` — server restart resets all flags to `appConfig` values. There is no persistence layer. If a user enables web search, restarts the server (e.g., for a codebase rebuild), web search is disabled again.
